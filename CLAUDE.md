# Nexa backend

API REST de Nexa (gestión de turnos de Loren Estudio de Belleza). Es el Proyecto Final de Grado de Emily Kohler **y** lo usa una clienta real en producción: tratar cada cambio como si pudiera llegar a producción. Node 24, Express 5, Prisma 6, PostgreSQL (Supabase), zod 4, JWT en cookies, Mercado Pago, Sentry, Supabase Storage, node-cron. TypeScript con `strict: false`, CommonJS. Comentarios y mensajes de error al usuario en español rioplatense.

## Estructura

- `src/app/`: `app.ts` (middlewares), `server.ts`, `routes.ts` (monta todos los routers bajo `/api`), `config/env.ts` (zod; si falta una variable el proceso hace `exit(1)`), `middlewares/errorHandler.ts` (`AppError`), `constants/http.ts`, `validators/datetime.ts`, `database/prisma.ts`.
- `src/modules/<modulo>/`: **las capas no son uniformes**, mirar el módulo vecino antes de crear uno. Lo común es `*.routes.ts` → `*.controller.ts` → `*.service.ts`. Algunos suman `*.repository.ts` (auth, invitations, professionals), `*.model.ts` (products, promotions, services, specialEvents), `dto/`, `middleware/`, `providers/`, `templates/`. `appointments` no tiene routes propio: `appointment.controller.ts` se monta desde `clients/client.routes.ts`, `professionals/professional.routes.ts` y `admin/`.
- `src/jobs/`: `scheduler.ts` registra los tres cron (node-cron) vigentes, todos cada 5 minutos: autoNoShow, releaseUnpaidAppointments y appointmentReminder (las campañas automáticas y el recordatorio de inactividad se eliminaron el 30/10/2026; el único mail que el sistema manda a las clientas por iniciativa propia es el recordatorio del turno, ver «Recordatorio de turno por mail»).
- `prisma/schema.prisma` y `prisma/migrations/`. `scripts/seed-demo.ts`. `src/generated/prisma` es generado.
- `tests/integration/*.test.ts`, `tests/helpers/{auth,factories}.ts`, `tests/setup.ts`.
- `00-gestion/` a `05-entregas/` es documentación académica y de gestión que forma parte de la entrega: no editarla salvo pedido expreso.

## Comandos

- `npm run dev` (tsx watch), `npm run build` (prisma generate + tsc), `npm start` (`dist/app/server.js`).
- `npm test` = `cross-env NODE_ENV=test vitest run`. Un solo archivo: `npx cross-env NODE_ENV=test vitest run tests/integration/auth.test.ts`; un caso: agregar `-t "texto del it"`.
- `npm run test:migrate`: `prisma migrate deploy` usando `.env.test`.
- `npm run typecheck` (solo `src`), `npm run typecheck:all` (`src` + `tests`, es el que corre el CI).
- `npm run seed:demo`.

## Tests

Necesitan un PostgreSQL de pruebas apuntado por `.env.test` (copiar de `.env.test.example`). `tests/setup.ts` aborta si `DATABASE_URL` no contiene "test", trunca todas las tablas antes de cada test (si agregás una tabla al schema, sumala a `TABLES`) y mockea mail y Mercado Pago. Sentry no se inicia con `NODE_ENV=test` (el DSN del `.env` llega a la corrida y mandaría cada falla provocada como error real). Los archivos corren en serie (`fileParallelism: false`). Los helpers `cookieFor()` y `factories.ts` evitan pasar por el login real.

## Reglas de arquitectura (verificadas en código)

- **Single-tenant por despliegue** (ADR-001): cada estudio tiene su propia base, backend y frontend. No hay `tenantId` ni `businessId` en el código: no agregar filtros de tenant ni inventar esa columna. En el frontend, el "tenant" es solo la marca (nombre, logo, colores y textos) cargada desde archivos fijos en `nexa-frontend/src/app/data/tenant/`; `VITE_TENANT_SLUG` está definida pero no se usa. Para un cliente nuevo se clona el sistema y se adaptan esos archivos y las variables de entorno.
- **Auth** (ADR-003, reescrito el 2026-10-24 con las limitaciones conocidas): JWT en cookies `httpOnly` `access_token` (15 min) y `refresh_token` (7 días, `path=/api/auth/refresh`, se guarda en base). En producción `sameSite=none` + `secure`. No hay header `Authorization`. **Sesiones por dispositivo**: cada dispositivo tiene una fila en `refresh_sessions` (máx. 10 por usuaria, el `sid` viaja en los dos JWT, se guarda el SHA-256 del refresh token); iniciar sesión en otro dispositivo no cierra los demás; `logout` cierra solo el dispositivo; cambiar/recuperar la contraseña, desactivar o anonimizar cierra todos. El refresh rota el token con control optimista y acepta el token anterior 30 s solo para renovar el access (dos pestañas a la vez). Para abrir una sesión usar `authService.startSession(user)`, nunca firmar tokens a mano. La columna `users.refresh_token` y el canje de las sesiones del formato anterior se quitaron (migración `20261028120000_drop_users_refresh_token`): un refresh token sin `sid` da `401 INVALID_REFRESH_TOKEN`. `logout` no exige sesión vigente. **CSRF**: la API no interpreta formularios (`express.urlencoded` quitado) y `middlewares/trustedOrigin.ts` rechaza con `403 FORBIDDEN_ORIGIN` todo pedido que cambia datos y trae un `Origin` distinto de `FRONTEND_URL`; no agregar un parser `urlencoded` ni cambiar `FRONTEND_URL` sin revisarlo. `change-password` exige `{ currentPassword, password }` (si la actual es incorrecta, `400 INVALID_CURRENT_PASSWORD`: nunca 401, el frontend desloguea ante cualquier 401). `reset-password` exige `{ email, token, password }`, busca el código de esa cuenta y limita a 5 intentos fallidos cada 15 minutos por email (`429 TOO_MANY_ATTEMPTS`). Los emails se guardan siempre con `trim().toLowerCase()` (el login los pasa a minúsculas) y se buscan sin distinguir mayúsculas (`mode: 'insensitive'`). Una invitación no puede pisar una cuenta admin ni una desactivada y se consume de forma atómica; el alta por invitación entrega las mismas dos cookies que el login (`auth/utils/cookies.ts`) y no devuelve el access token en el cuerpo. Rutas protegidas con `authenticate` + `authorize(...roles)` / `requireRole(...)`; roles `client`, `professional`, `admin`. El secreto mínimo es 32 caracteres.
- **Validación** (ADR-002 en espíritu): zod en el borde (DTOs en `dto/` o `.safeParse` en el controller) y se responde con código `VALIDATION_ERROR`: `400` en casi todos los módulos (usar este), `422` solo en `auth.controller.ts`. Fechas `YYYY-MM-DD` y horas `HH:mm` como texto, con `dateSchema`/`timeSchema` de `src/app/validators/datetime.ts`.
- **Hora de Argentina**: los turnos son texto en hora de Argentina (UTC-3, sin horario de verano) y el servidor de producción (Render) corre en UTC. Nunca usar `new Date('YYYY-MM-DDTHH:mm:00')` sin zona, `getHours()`/`getDate()` ni `toISOString().slice(0, 10)` para "hoy" o para comparar con un turno: usar `todayArgentinaStr()`, `appointmentInstant(date, time)` y `argentinaParts()` de `src/app/utils/argentinaTime.ts`. Los cron usan `timezone: 'America/Argentina/Buenos_Aires'`. No fijar `TZ` en el servidor: `toAdminView` y `normalizeAdminUpdateInput` dependen de que el proceso esté en UTC. Los tests corren con `TZ=UTC` (`vitest.config.mts`) para reproducir producción. Los jobs (recordatorio de turno, inasistencia) y los dashboards también lo usan; para rangos de calendario (día, semana, mes, año) con getters locales hay `argentinaWallClock()`, que NO es un instante real y no se compara con fechas de la base.
- **Errores**: lanzar `new AppError(HTTP.X, 'mensaje', 'CODIGO')` y el handler responde `{ error, code }`. Cualquier otro error se loguea en el servidor y al cliente sale un 500 genérico: nunca devolver `err.message` de Prisma.
- **R-01, disponibilidad de la profesional** (ADR-002): la garantía es el índice único parcial `appointments_professional_date_time_active_key` sobre `(professional_id, date, time) WHERE status NOT IN ('cancelled','cancelled_no_show') OR slot_locked`, creado solo en SQL de la migración (la última, `20261031120000_turno_horario_original_bloqueado`) (no es `@@unique` de Prisma; no perderlo al tocar el schema). No hay consulta previa: se hace el `INSERT` y `isSlotConflict()` traduce la violación a `409 PROFESSIONAL_SLOT_TAKEN` (eventos especiales: `SLOT_TAKEN`; sin profesional libre: `NO_PROFESSIONAL_FREE`). La reserva de la clienta fuera de franja devuelve `400 OUT_OF_HOURS` (`assertWithinAvailability`); los turnos manuales del admin/profesional no se validan a propósito. **Limitación conocida**: el índice compara la hora de inicio, no detecta solapamientos por duración; la verificación por duración existe solo para los inicios de un horario reabierto (más abajo).
- **Inasistencia, horario reabierto y reserva tardía** (AE4, fase 2; reglas confirmadas por escrito por la propietaria el 30/10/2026; lógica en `src/modules/appointments/reopenedSlots.ts`): el job `autoNoShow` pasa a `no_show_auto` («No asistió (automático)») un turno `confirmed` sin llegada registrada con MÁS de 30 minutos de su hora de inicio (30 exactos no). `no_show_auto` sigue ocupando el horario (no está en el predicado de exclusión del índice), no suma a la carga semanal de `resolveProfessionalId`, la clienta no lo cancela (`cancelForClient` solo acepta `pending` y `confirmed`) y la seña (`paymentStatus`) no cambia. El personal marca `cancelled_no_show` (solo desde `confirmed` o `no_show_auto` y desde la hora de inicio: antes, `400 NO_SHOW_BEFORE_START`) y puede corregir `no_show_auto`/`cancelled_no_show` a `finished` siempre y a `confirmed` solo sin superposición (`409 APPOINTMENT_OVERLAP`); todo cambio de estado va por `changeStatusByStaff`. El horario ORIGINAL nunca se reabre: `appointments.slot_locked` (true en `cancelled_no_show` y en `cancelled` hecha después de la hora de inicio) mantiene la fila dentro del índice; se escribe en la MISMA sentencia que cambia el estado. Si la marca ocurre hasta 40 minutos después del inicio se crea una fila de `reopened_slots` (inicios cada 5 minutos desde el siguiente múltiplo de 5 a la marca, hasta 60 minutos después de la hora original inclusive; el servicio tiene que entrar en la franja y no pisar ningún turno activo; reserva bajo `lockProfessionalDay`). Reserva tardía de la clienta: hasta 15 minutos después de la hora de inicio, después `400 START_TIME_PASSED` (el personal queda exento). El backend sigue aceptando cualquier hora dentro de la franja (no impone la grilla de 120 minutos del frontend); el frontend tiene que usar `reopenedStarts` y `earliestStart` de `GET /api/professional/:id/availability`, no el reloj del navegador. Códigos nuevos: `NO_SHOW_BEFORE_START`, `INVALID_STATUS_TRANSITION`, `APPOINTMENT_OVERLAP`, `NOT_CANCELLABLE`, `START_TIME_PASSED`, `REOPENED_SLOT_CLOSED`, `REOPENED_SLOT_UNAVAILABLE`, `SERVICE_DOES_NOT_FIT`. Las entradas de actividad que tocan un turno llevan `activity_logs.appointment_id`.
- **Tienda: lista pública, lista del administrador y libro de inventario** (AE4, fase 4): `GET /api/store/products` es pública y devuelve SOLO productos `active` con `stock > 0`, con `select` explícito (`id`, `name`, `brand`, `category`, `description`, `imageUrl`, `price`) más `available: true`; nunca `stock`, `minStock` ni `status`. Todos los productos (inactivos y sin stock, con `stock` y `minStock`) salen por `GET /api/admin/store/products`, solo administrador (router de `admin/`); el alta, la edición y la baja siguen en `POST|PUT|DELETE /api/store/products` (admin). `orderService.createForClient` rechaza con `400` un producto que no existe o no está `active` (`PRODUCT_NOT_FOUND`, incluye `out_of_stock` e `inactive`) y una cantidad mayor al stock sumando las líneas del mismo producto (`INSUFFICIENT_STOCK`), sin importar lo que mande el navegador; el stock NO se descuenta al crear el pedido. Al aprobarse el pago (Mercado Pago o confirmación del administrador por WhatsApp), `applyPaymentResult` descuenta el stock y crea un `InventoryMovement` de salida por producto (cantidades de las líneas sumadas, nota `Venta — pedido <id>`, fecha `todayArgentinaStr()`) en la MISMA transacción que reclama el pedido, así que un aviso repetido no duplica nada. El movimiento no tiene `orderId`: si el administrador edita o borra desde el libro un movimiento de venta, el stock se corrige en consecuencia.
- **Cancelación y devolución de la seña** (AE4, fase 3; lógica en `src/modules/appointments/cancellationRules.ts`): el sistema solo MARCA la seña como devuelta (`paymentStatus = 'refunded'`), no ejecuta ninguna devolución en Mercado Pago. `refundPolicy` admite solo `full` o `none` (validado en `PATCH /settings/payments`; los `partial` viejos se migraron a `full`). La clienta cancela desde la app solo turnos `pending` o `confirmed` (también ya empezados): con la seña paga (`partial` o `paid`) y `cancellationHours` (12 por defecto) o más entre ahora y el inicio, se marca `refunded`; con menos, queda retenida; si no estaba paga, no se marca nada; con `none`, siempre retenida. El PATCH del personal con `status: 'cancelled'` EXIGE `cancelledBy` (`client` o `studio`, `400 VALIDATION_ERROR` si falta) y admite `clientNoticeAt` (ISO, por defecto ahora, no futura: `400 INVALID_NOTICE_TIME`; la profesional hasta 48 horas atrás, más antiguo solo el administrador: `403 NOTICE_TOO_OLD`), `noticeChannel` (`whatsapp`, `call`, `in_person`, `other`) y `noticeNote` (hasta 200). `studio` devuelve la seña paga sin mirar la hora ni la política; `client` cuenta las horas de aviso (inicio menos `clientNoticeAt`; un aviso posterior al inicio se acepta y no devuelve). Se guardan `cancelled_by` (`client`, `studio` o `system` para la liberación por falta de pago) y el aviso completo (quién lo cargó, cuándo, hora, medio y nota), que el detalle del turno (`cancellation`) y el registro de actividad muestran. Combos: el personal cancela todo el grupo, la clienta solo su pata, y la devolución se decide UNA sola vez (en el grupo, o en la última pata activa). Cancelar un turno ya empezado, o liberarlo por falta de pago, bloquea el original y, hasta 40 minutos después del inicio, abre un horario reabierto. El mail a la clienta sale solo cuando cancela o reprograma el personal (más el recordatorio, abajo).
- **Datos personales y alergias** (AE4, fase 5; ejecutor: `adminService.anonymizeClient`, `POST /api/admin/clients/:id/anonymize`): además de nombre, apellido, correo, teléfono, cuenta inactiva y sesiones cerradas, borra las fotos de la galería (filas y archivos del bucket con `uploadProvider.deleteImages`, que nunca lanza: lo que no se pudo borrar queda en una entrada de actividad de nivel `error` con la lista) y vacía teléfono, dirección y notas de los pedidos y el texto de las reseñas (el puntaje se conserva). Se conservan turnos, pagos, montos de pedidos, alergias, preferencias, observaciones y notas. Los cambios en la base van en una sola transacción y los archivos se borran después de confirmarla; la entrada de actividad enumera los campos tocados con cantidades y quién la ejecutó. **RNF-03**: `listClientsForProfessional` y `toProfessionalView` (agenda y respuestas de turnos de la profesional) devuelven la alergia del perfil (`Client.allergies`) solo si la profesional tiene al menos un turno `finished` con esa clienta; la alergia de un turno (`details.allergies`) la ve la profesional asignada a ese turno. Ningún endpoint escribe `Client.allergies` (la clienta carga `Appointment.allergies` con consentimiento y el admin recibe `400` si intenta cambiarla): no agregar uno.
- **Recordatorio de turno por mail** (AE4, fase 3b; regla de la propietaria, decisión de la autora del sistema, Emily, 31/10/2026: no hay constancia escrita nueva y no hace falta para desplegar; lógica en `src/modules/appointments/reminder.ts`, job `src/jobs/appointmentReminder.job.ts`): cada 5 minutos se manda UN mail por turno (o por grupo de combo, con todos los servicios) cuando faltan 5 horas o menos para el inicio y hasta 1 hora antes (con menos de 1 hora no se manda). Solo `confirmed` con seña paga (`partial`/`paid`) o sin seña requerida. NO se manda si la reserva se creó con menos de 5 horas de anticipación (`createdAt` contra el inicio; 5 exactas sí), si el correo no está verificado, si la cuenta está desactivada o anonimizada (`users.active = false`) o si la clienta está bloqueada. `appointments.reminder_sent_at` se escribe ANTES de enviar con `updateMany` condicional (`reminder_sent_at IS NULL`, mismo `status`) y se vuelve a `null` si el envío falla, así que nunca se reenvía y dos corridas no mandan dos mails; cae el proceso entre la marca y el envío y ese recordatorio se pierde (se prefiere a duplicarlo). Reprogramar el turno (la clienta con `rescheduleForClient`, o el personal cambiando fecha u hora en `updateForProfessional`/`updateForAdmin`) vuelve `reminder_sent_at` a `null`: el nuevo horario recibe su propio recordatorio si cumple las reglas (ojo: `createdAt` no cambia al reprogramar, así que la regla de las 5 horas de anticipación se mide desde la reserva original hasta el nuevo inicio). Un cambio del personal que no mueve fecha ni hora no limpia la marca. Si el mail falla se reintenta en cada corrida hasta 1 hora antes y queda UNA entrada de actividad de error por turno (`appointment_id`); cada envío exitoso deja otra. El job recibe `now` por parámetro (reloj inyectable) y el scheduler lo registra con `noOverlap`. El mail trae tres botones que son enlaces a la web, `FRONTEND_URL/mis-turnos?turno=<id>&accion=ver|reprogramar|cancelar`: no ejecutan nada (la web exige sesión y confirmación) y solo llevan el id del turno (en un combo, el de la primera pata). Aviso de la seña (solo si hay seña paga): «Si cancelás ahora (con menos de 12 horas), la seña no se devuelve», con las horas de `cancellationHours`; con `refundPolicy = none` dice «Si cancelás, la seña no se devuelve.» y si queda más tiempo que la ventana configurada lo aclara en vez de afirmar algo falso. La plantilla es `appointments/templates/appointmentReminder.html` y escapa todo texto cargado por personas. La política de privacidad lista este mail desde la versión `2026-11` (`PRIVACY_POLICY_VERSION`); el texto de la política vive en el frontend (`PrivacyPolicyPage.tsx`) y la constante tiene que subirse en los dos repositorios.
- **Brechas de requisitos** (AE4, fase 6): (1) **Teléfono (RF-02):** todo `User.phone` pasa por `src/app/validators/phone.ts` (`phoneSchema` en zod, `assertValidPhone` donde no hay zod): celular argentino, expresión `/^(?:\+?54)?9?0?[1-3]\d{1,3}(?:15)?\d{6,8}$/` sobre el valor sin espacios, guiones ni paréntesis, más 10 dígitos de código de área + número sin prefijos; se guarda tal cual (solo `trim`), el vacío vale en las ediciones del personal y en el perfil, no en el registro. (2) **Servicio especial (RF-03/RF-17):** nace `paymentStatus = 'pending'` y paga con Mercado Pago como cualquier turno; `releaseSpecialSlot` (`appointments/specialSlots.ts`) devuelve su horario (`specialSlots[].appointmentId`) en la misma transacción en TODA cancelación (job de impagos, clienta, personal), tomando primero el lock del servicio (`FOR UPDATE`), igual que al reservar. (3) **Antigüedad (RF-06):** `professionals.joined_at` (nullable, la carga el administrador, no futura) con `createdAt` por defecto; desempata `resolveProfessionalId` a igual carga semanal. (4) **Categoría (RF-11):** `unas`, `cabello`, `cuerpo` y `rostro`; `combo` solo con `isCombo`; se revisa al crear y al editar si el pedido trae `categoryId` o `isCombo`. (5) **Liberación por seña impaga (RF-14/RNF-05):** una entrada de actividad por turno (`appointment_id`). (6) **Avisos (RF-24):** solo existen los tipos que algo emite (`new_appointment`, `cancelled_appointment`, `rescheduled_appointment` para la profesional; `new_service`, `new_product`, `new_promotion`, `special_service` para la clienta). (7) **Sin ingreso con Google/Facebook (RNF-07):** no agregar un proveedor social ni sus variables sin pedido expreso.

## Seguridad

- Nunca loguear ni devolver tokens, cookies, datos de pago ni contenido de `.env`. `beforeSend` de Sentry (`src/sentry.ts`) descarta errores de validación y 404 y, con `scrubSensitiveData`, borra cookies, cuerpo, query string, cabeceras sensibles y email/IP del usuario. Los mensajes de error y los `console.error` igual pueden llegar a Sentry: no meter datos sensibles en ellos.
- **Mails**: todo mail sale por `mailProvider` (`auth/providers/mail.provider.ts`); ningún otro módulo debe hablar con un servidor de correo ni nombrar una dirección. En producción se envía por la API HTTPS de Brevo (`BREVO_API_KEY` solo en Render): Render bloquea el SMTP en el plan gratis (`ETIMEDOUT`/`ENETUNREACH` en el puerto 587). Sin esa clave se usa SMTP, solo para desarrollo. El remitente es siempre `MAIL_FROM` (`kologic6@gmail.com`), verificado como remitente en Brevo. Los envíos que no deben delatar si una cuenta existe (recuperar contraseña, registro) no esperan al mail: un fallo queda solo en el log del servidor (`[mail] ❌`).
- Webhook de Mercado Pago: Mercado Pago reintenta cada 15 minutos (y cada vez más espaciado) hasta recibir 200, y no está documentado que el `ts` se renueve, así que **no** se rechazan avisos por antigüedad. La protección contra repeticiones es la idempotencia: `applyPaymentResult` y `applyGroupPaymentResult` usan escrituras condicionales (`updateMany` con `paymentStatus` distinto del final), no un chequeo previo. Antes de marcar algo como pagado se compara el monto y la moneda que informa Mercado Pago con la seña o el total esperado (`payments/paidAmount.ts`): si no coinciden no se registra y queda un aviso de error en la actividad. El webhook responde 200 después de procesar y 500 si falló algo transitorio (para que Mercado Pago reintente); no loguear el objeto de error completo del SDK.
- `helmet` con CSP `default-src 'none'`, rate limit global (100/min) y limiters propios en `auth.routes.ts` (desactivados con `NODE_ENV=test`), CORS con `origin: FRONTEND_URL` y `credentials: true`, `trust proxy` en 1.
- Webhook de Mercado Pago: `POST /api/webhook/mercadopago`, protegido por `verificarFirmaMercadoPago`.
- Uploads: `POST /api/uploads/image`, multer en memoria, 5 MB, sube a Supabase Storage.
- `.env` y `.env.test` tienen credenciales reales de infraestructura: no leerlos ni imprimirlos, usar los `.example`.

## Forma de trabajar

- **Context7 siempre que se pueda.** Antes de escribir o cambiar código que dependa de una librería (Express 5, Prisma 6, zod 4, Vitest, Supertest, multer, node-cron, Mercado Pago, Sentry, Supabase), consultar su documentación vigente con el MCP `context7` (`resolve-library-id` y después `query-docs`). No usarlo para lógica de negocio propia. En las consultas no pegar código del proyecto ni datos reales.
- **Bitácora obligatoria.** Todo cambio en el código, la configuración o GitHub (ediciones, borrados, commits, push, ramas, pull requests) se anota en `00-gestion/20261028_BitacoraIndividual_KohlerAE3_v1.md` (bitácora de la AE3, continúa la de la AE2) con fecha y hora exactas y los seis elementos: qué se decidió, alternativas y criterio de descarte, evidencia, aporte personal, desacuerdo y resolución, y herramienta auxiliar. Las entradas se agregan al final, en el mismo cambio que las motiva.
